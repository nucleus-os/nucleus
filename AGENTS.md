# Nucleus Agent Guide

Nucleus is a monorepo built with Swift 6.4 through SwiftPM.

## Default Engineering Posture

- Prefer the ideal long-term architecture over compatibility shims, dual preserved pipelines, feature-flagged old paths, or deprecated wrappers.
- Delete replaced APIs directly and fix all callers in the same change. If dead code falls out, remove it.
- Hard-require modern Vulkan/kernel/toolchain features when they fit. For Vulkan, append required extensions where the renderer declares its instance/device requirements; failing device creation is correct when requirements are missing.
- Match macOS patterns for compositor work and iOS patterns for RN library work, then account for Linux/Wayland/io_uring/Vulkan constraints.
- Do not add protocol or schema version identifiers to internal contracts whose producers and consumers always ship from the same monorepo build and cannot realistically drift. For persisted state, prefer a one-time hard migration to the new shape or a deliberate reset over preserving readers for old formats. Add a version only when a documented boundary genuinely requires one implementation to accept multiple concurrently possible formats, such as independently deployed endpoints; persistence by itself is not such a boundary.
- Do not add magic bytes by default. Magic is justified only when a parser must resynchronize after entering an unframed byte stream at an arbitrary offset, distinguish multiple formats that genuinely share one transport or storage location, or reject the wrong file type before parsing untrusted input. A dedicated socket or file path, authenticated peer, framed transport such as `SOCK_SEQPACKET`, operation discriminator, exact packet/structure size, or same-build producer and consumer is not a reason to add magic. State the concrete ambiguity or resynchronization requirement beside any new magic value.
- Swift visibility follows the supported consumer boundary. `public` is for declarations consumed outside the root Nucleus package, `package` is the default for first-party cross-module API, and implementation details remain `internal` or narrower. The manifest dependency graph restricts which targets may use package API. `public import` is import access control, not re-export syntax; deliberate facades use `@_exported import`. First-party SPI requires a concrete external-package consumer and never exists for tests, harnesses, or same-package production code.
- The supported external Swift source products are `Nucleus`, `NucleusDesktop`, `NucleusReactRuntime`, `NucleusFoundation`, `NucleusSessionProtocol`, and `NucleusAndroidRuntimeCore`. A dynamic library is a deployment boundary, not automatically a public source contract.
- Do not provide wall-clock estimates. Scope work by files, structural moves, dependencies, and risk surface.

## Workflow Directives

- The user may edit concurrently. Never revert changes without explicit permission, even if they break builds.
- When asked to commit or push, do it on the current branch (including `main`). Create a new branch only when the user explicitly asks for one; do not branch off `main` by default.
- Run build and test verification through the installed `collider` command. Its workspace launcher derives the host environment and refreshes the release Collider executable whenever the current Git/toolchain source fingerprint changes. Do not source `tools/host-env.sh` manually or invoke `collider/.build/.../collider` directly.
- Format touched Swift files with the pinned toolchain's `swift-format`; the root `.swift-format` is the repository-wide formatting contract. Do not combine an unrelated repository-wide reformat with functional work.
- Do not write tests that inspect source-code shape or declaration presence/absence, such as `@hasDecl` assertions for APIs that should not exist. Test behavior and runtime contracts instead.
- Avoid full cache wipes (`rm -rf .build`) except as a last resort after source/build causes are ruled out, or if disk space is full.
- Do not launch the compositor/app, start manual interactive sessions, or run long-lived foreground processes without explicit user request.
- A goal may be marked complete when implementation and every agent-runnable verification gate are complete and the only remaining step is the user's own validation or interactive run. State that handoff explicitly; user-owned validation does not keep the goal open.
- React 19 and React Compiler are enabled. Do not use `useMemo`, `useCallback`, etc.
- Do not patch the vendored React Native tree. Public RN compatibility is required; pnpm patches against dependencies are allowed.
- When writing plans, use strict sequential phase order. Do not describe phases as parallel.
- Plans must avoid git/PR/commit/branch/release mechanics. Use technical ordering language like "lands with", "happens alongside", and "as part of phase N".
- Plan voice is direct and unambiguous. Write the ideal solution without hedging between options.
- When writing a new doc or plan under `docs/`, just write it. Do not read other docs or study formatting conventions first; use the structure these directives already specify (state invariant first, strict sequential phases, direct voice) and a `kebab-case.md` filename.
- The plan inventories in `docs/README.md` and component documentation indexes are authoritative. Add every new plan to its owning inventory and keep execution order there rather than duplicating it across plans.
- Update a plan in the same change that starts, completes, supersedes, removes, or materially changes one of its phases. Every plan states one lifecycle status: `active`, `deferred`, `complete`, or `superseded by <document>`. A phase without an explicit status is pending in the declared sequence; set `Status: active`, `Status: complete`, or `Status: superseded by <document>` as its lifecycle changes.
- A completed phase records the achieved state and concise gate evidence. Do not maintain chronological progress journals, duplicate command transcripts, or stale checklists.
- Remove a completed or superseded plan from the active execution order immediately. Keep completed plans under the owning inventory's architecture-consolidation section until their durable invariants move into architecture or contract documentation, then delete the plan. A superseded plan identifies its replacement and leaves the active inventory.
- After an architectural change, re-audit every downstream phase against the codebase and rewrite or delete stale work before continuing. Do not execute an old phase literally merely because it remains written down.
- When debugging, inspect newest relevant logs/profiles/screenshots first, add diagnostics before speculative fixes, and do not attempt more than one speculative fix without log-based evidence.
- Containers never access external networks. Every dependency lookup, resolution, download, and source acquisition runs on the host, produces a pinned local input, and completes before container execution. Containers consume only mounted source, caches, locks, SDKs, and artifacts while compiling, testing, assembling, and packaging. If container work attempts network access, move that acquisition to a host action instead of enabling networking, adding retries, or changing package-manager behavior.
- Do not stop mid-task to check in when the work is within capability. Ask only for genuine design forks, destructive actions, or blockers requiring user input.

## Build System

- Single opinionated build: all integrations compile, no profiles or feature flags.
- The authoritative development checkout lives on macOS. Remote clients access that checkout through standard private SSH and editor integration and invoke the installed `collider` command on the Mac. Do not introduce a persistent Linux development machine, source-snapshot service, Collider worker daemon, remote-execution protocol, or second development checkout. Linux containers remain offline build executors and never own developer source or credentials.
- The first-party runtime graph is one SwiftPM package rooted at `Package.swift`: `core/` owns the portable render/UI core and Android host, `react-native/` owns the RN platform and native stack, `compositor/compositor-core` and `compositor/compositor` own the Wayland/DRM library and executable, and `shell/` owns the out-of-process desktop shell. Third-party source remains in root-managed submodules. The build/test/run tool is the separate `collider` package at `collider/` (the `collider` executable and `ColliderCommands`) plus its `collider/engine/` package (`ColliderCore`/`ColliderRuntime`/…). Collider consumes the root package only through `NucleusSessionProtocol` and `NucleusAndroidRuntimeCore`. Run `./collider-setup.sh` once on a fresh clone to provision the host toolchain when necessary, build the optimized binary, and install the `collider` command on PATH. Setup never provisions workspace artifacts. Thereafter run `collider` from any directory inside the clone for complete-checkout doctor/bootstrap/build/test operations; every operation materializes its own prerequisite graph. The installed shim delegates to `tools/collider-launcher.sh` in that clone, which derives the host environment and asks SwiftPM to refresh the release executable whenever the Git/toolchain source fingerprint differs from the successful build. The executable rejects direct invocation, and Collider refuses to run outside a clone.
- The first-party JavaScript workspace under `react-native/` uses Bun and `bun.lock`. Its exact published `react-native` package supplies the JavaScript runtime, generated TypeScript declarations, codegen scripts, ReactCommon, and generated FBReactNativeSpec sources consumed by Collider; there is no upstream Yarn dependency graph. The matching unmodified canonical React Native gitlink supplies only `ReactCxxPlatform`, which the npm package omits. The separate Hermes checkout remains the source of the Hermes engine Nucleus compiles. Do not replace Bun or reinterpret `bun.lock` with another package manager.
- External networks belong exclusively to host-side acquisition actions. Every OCI execution uses the host-only Apple container network with DNS disabled and cannot request external access. Host SwiftPM resolution materializes the exact `Package.resolved` closure into the mounted scratch/cache before Linux compilation, and host Bun installs the exact `bun.lock` closure for Linux multiarch before React Native container work. Containers compile, test, assemble, and package only already-materialized inputs.
- First-party C/C++ shims consumed by Swift are SwiftPM C targets plus module maps. C++ libraries (Skia Graphite, ReactCommon/Hermes/folly) are reached via C++ interop. Every Swift target sets `.interoperabilityMode(.Cxx)`; there is no non-cxx tier, so which module may import which is never a build question. Keeping C++ types out of Swift domain models remains the rule, held by review rather than by the module graph: the boundary carries opaque handles, scalars, and value structs of those. A Swift→C++ callback seam is a `std::function` typedef in the public header, which Swift satisfies with `.init { … }` over a thick closure (`MountingObserver.hpp`, `ReactRuntimeHostFacade.hpp`, `TextLayoutManager.hpp`, `TurboModuleRegistry.hpp`). Swift implements a C++ virtual interface through an abstract base in the header plus a bridge subclass holding those closures, either file-local in an anonymous namespace behind a `noexcept` factory returning `shared_ptr` (`SwiftMountingObserverBridge.cpp`) or constructed directly (`NucleusPlatformTimerRegistry`). A first-party C++ seam carries no `void *` context pointer, no paired release callback, and no `@convention(c)` trampoline; `std::function` owns its captures and destroys them. Because that destruction releases Swift captures and can run arbitrary deinitializers, a replaced or cleared callable drops outside any lock the seam holds, or teardown deadlocks by re-entering the seam. `@convention(c)` is correct only where an external C library demands a function-pointer vtable (libwayland listeners, libdrm event handlers, PAM conversation). Seams the Swift side owns end to end stay Swift protocols and are not interop at all (`RenderUploadSink` in `NucleusAppHostProtocols`). Genuine Swift→C entry points (the JNI/on-device and headless-test harnesses) use `@c` / `@c @implementation`, which type-check C-compatibility and emit the C declaration.
- Two constraints follow from every target parsing C headers in C++ mode. A first-party C header declaring a non-inline function wraps it in `extern "C"` guards, or the caller emits a mangled reference the C implementation never defines — which surfaces at link, not compile, with a demangled signature in the error. `static inline` façades (`NucleusLinuxDBusC.h`) are exempt because they emit per translation unit and need no linkage agreement. Separately, Swift cannot catch C++ exceptions: an entry point into a throwing C++ library is `noexcept` with an internal catch-all, or the process terminates.
- The native C++ stack is provisioned into per-target roots such as `~/.cache/nucleus/nucleus-native-sdk/linux-arm64`, split into `render` (owned by `core/`), `rn` (owned by `react-native/`), `wayland` (owned by `swift-wayland/`), and `android/gfxstream` (owned by `android-runtime/`). Linux/amd64 and Android/arm64 use sibling target roots. Skia, gfxstream/Mesa, Wayland, Hermes, React Native C++, and their compiler caches live in component-and-target-specific Collider workspaces; only finished libraries, generated public headers, pkg-config metadata, and required host tools enter the staged native SDK. The top-level staged bootstrap owns the complete dependency order and artifact fingerprints.
- Linux Swift target-runtime and SwiftPM compilation/link intermediates live in architecture-specific Collider persistent workspaces, with compiler caches in separate architecture-specific workspaces. The host owns read-only source and dependency inputs plus bounded runtime, SDK, and SwiftPM product exports; containers never bind-mount a host Linux `.build` directory.
- Collider container storage has four disjoint classes: read-only host inputs, bounded writable host exports modeled as action outputs, named persistent workspaces for materialized case-sensitive Linux source, intermediates, and compiler caches, and tmpfs for `/tmp` and the container home. Each source, build, and compiler-cache role uses a separate workspace; AOSP source is materialized offline from a host-owned partial-clone Repo cache whose exact locked trees are fully hydrated by host networking. It is never authoritative source. `OCIMount` never represents general writable scratch storage. Deleting every owned workspace must preserve all authoritative inputs and finished artifacts and leave every product reproducible.
- The Swift 6.4 target-runtime source closure under `swift-sdk/source/` contains `libxml2`, `llvm-project`, `swift`, `swift-collections`, `swift-corelibs-foundation`, `swift-corelibs-libdispatch`, `swift-corelibs-xctest`, `swift-experimental-string-processing`, `swift-foundation`, `swift-foundation-icu`, `swift-sdk-generator`, and `swift-testing`. Modified repositories point at genuine `nucleus-os` forks and unmodified repositories point at canonical upstreams. Collider validates but never selects, fetches, resets, cleans, patches, or materializes that source. macOS uses Xcode and the Apple-container Linux/arm64 builder uses the matching official Swift.org compiler as a bootstrap compiler. Nucleus never builds the Swift compiler, Swift driver, LLVM, Clang, SwiftPM, SourceKit-LSP, DocC, or another host toolchain. Upstream `build-script` configures the pinned LLVM CMake source for the amd64 cross host with an empty build target list. `collider build swift-sdk --rebuild` builds the Linux target standard library and overlays, Dispatch, Foundation, XCTest, and Swift Testing natively for arm64 and by cross-compilation for amd64, assembles both into one Linux Swift SDK artifact, and installs the official Android Swift SDK artifact.

### Prerequisites

A fresh clone installs the `collider` command with `./collider-setup.sh`. Run
`collider doctor` to validate the host, then `collider build`; the build owns and
materializes its complete target-SDK and native-artifact prerequisite graph.
`collider bootstrap <component>` remains an explicit way to provision a native
dependency closure without building the Swift products.

Skia third-party dependencies are synced by Collider:

```sh
collider bootstrap core
```

The published React Native package provides its generated FBReactNativeSpec sources. The
RN native builds live in **`react-native/`**, not `core/`.

## Submodules

Submodules are detached HEADs. If one needs first-party patches, use a genuine upstream fork under `nucleus-os`, repoint the submodule at the fork, and push over SSH: `git push origin HEAD:refs/heads/<branch>`.

AOSP is the exception to root submodule ownership. Its source graph remains owned by an exact Repo manifest: modified projects point at genuine `nucleus-os` forks and exact revisions, while unchanged projects retain canonical upstream remotes. Do not duplicate Repo-managed AOSP projects as monorepo submodules.

The monorepo root is the source-control and release boundary. First-party package directories are not submodules.
