# Apple Swift package adoption

Status: active

## Invariant

First-party Swift code uses the standard library for synchronization. It uses a
maintained Apple Swift package when that package directly owns a collection,
complete-span parsing, or asynchronous-composition invariant that Nucleus would
otherwise have to reproduce across parallel state or manual bounds and
cancellation handling.

Externally structured binary input that is available as one complete span uses
`swift-binary-parsing` unless an external schema already owns its encoding. A
protobuf payload uses generated `SwiftProtobuf` types from its authoritative
`.proto` schema. Keyed state whose correctness depends on a parallel ordering
array uses an ordered collection. A FIFO whose admission path removes from the
front uses a deque when its size is not inherently tiny. A merged asynchronous
sequence has an explicit terminal event and cancellation path.

Purpose-built state machines remain purpose-built. Incremental parsers that must
distinguish incomplete input from malformed input, bounded tiny arrays,
same-build hot-path payload readers, structured task races, and clear loops do
not acquire package abstractions that weaken their contracts or merely shorten
their spelling.

`swift-collections`, `swift-algorithms`, `swift-async-algorithms`,
`swift-atomics`, and `swift-protobuf` are already resolved and checked out by
the repository's package graphs. Declaring a direct dependency on any of them
changes no pinned version, adds no fetch, and adds no checkout. The only new
package is `swift-binary-parsing`. Its macro target also brings SwiftSyntax into
the resolved graph. The root package and the `swift-java` fork therefore declare
the upstream SwiftSyntax URL at the exact revision already pinned by the
`third-party/swift-syntax` gitlink,
`050f1a346fbbac0ca2cfb15a95274f7bd1cf0ccf`. One URL and one revision own the
SwiftPM identity across direct and transitive edges; mixing a local path with
BinaryParsing's upstream URL is forbidden because SwiftPM warns today and will
reject that conflict in a future release.

Container execution never resolves. Every dependency this plan declares is
materialized by host-side SwiftPM resolution into the mounted scratch and cache
before Linux compilation, under the standing acquisition rule.

## Phase 1: A parsing library replaces the hand-written complete-span readers

Status: complete

`swift-binary-parsing` is a declared dependency of the root package at
exact version `0.0.2`, revision
`2655f40f579c686d44687ac4fed54c73c3c4be2e`. The package is pre-1.0 and permits
source-breaking minor releases, so the manifest uses an exact requirement. The
`BinaryParsing` product attaches to `NucleusCompositorPolicy`,
`NucleusCompositorWaylandRuntime`, `NucleusCompositorRendererLinux`, and
`NucleusAndroidContainerContract`. `swift-protobuf` is a direct root dependency
at exact version `1.38.1`, and its `SwiftProtobuf` product also attaches to
`NucleusAndroidContainerContract`. Root and SwiftJava SwiftPM dependencies use
the upstream SwiftSyntax URL at the gitlink's exact Swift 6.4 snapshot revision,
eliminating the duplicate local-path/remote-URL package identity.

Four independent readers now share the package's bounds and overflow discipline:

- `XCursor.Reader` is deleted. Xcursor file headers, TOC records, image headers,
  and pixels consume a `ParserSpan`; fixed-stride extraction bounds table and
  pixel byte counts before iteration or copying.
- `AndroidApexArchive` no longer extends `Data` with a second reader. ZIP end,
  central-directory, and local-file records have parsing initializers;
  filesystem probes use checked seeks and integer parsing. The AOSP
  `apex_manifest.proto` schema is pinned at revision
  `75c8ee81684d118ef3af2a4e898b8835da0be0c8`, its checked-in Swift source is
  generated by the matching SwiftProtobuf 1.38.1 plugin, and archive metadata is
  decoded with the generated `ApexManifest` message before Nucleus validates a
  nonempty name and positive signed version. `collider generate android-runtime`
  owns regeneration through a repository command plugin backed by the pinned
  `protoc` and `protoc-gen-swift` products; it stages output and atomically
  publishes only a changed generated file. `collider test android-runtime`
  regenerates into plugin-owned scratch and fails on drift without modifying the
  checkout.
- `parseInFormatsBlob(_:)` bounds both fixed-stride tables before walking them,
  so count multiplication and offsets cannot overflow ahead of validation.
- The Xwayland property parsers bound client-controlled `value_len` against the
  xcb reply's actual response length before creating a `ParserSpan`. Integer and
  atom decoding no longer performs direct unaligned loads.

`PamHelperWire.ResponseParser` is not converted. It parses incrementally across
arbitrary pipe fragmentation and must distinguish incomplete from malformed on
every append, which is a state machine over a growing buffer rather than a parse
of a complete span.

`PaintPayload` is not converted. `readUInt32(_:_:)` and `readFloat(_:_:)` decode
a blob whose producer and consumer ship from the same build, on a per-frame path,
where a throwing bounds-checked parser is the wrong trade.

Gate evidence: `collider test android-runtime` and `collider test compositor`
pass. Xcursor, DRM, APEX, and Xwayland coverage rejects oversized fixed-stride
tables, truncated records, malformed protobuf messages, nonpositive APEX
versions, and xcb declared-length/response-length mismatches. APEX coverage also
proves standard protobuf unknown-field and last-singular-field semantics. Root
and Collider resolution files record BinaryParsing version `0.0.2` at the
declared revision, SwiftProtobuf version `1.38.1`, and SwiftSyntax at the declared
snapshot revision. Resolution and Collider test output contain no
conflicting-identity warning. `collider generate android-runtime` reproduces the
checked-in source byte for byte, and the Android-runtime test route includes its
non-mutating generated-source verification task.

## Phase 2: Ordered collections replace parallel order state

Status: active

`swift-collections` becomes a declared dependency of the root package. The
`OrderedCollections` product attaches to
`NucleusCompositorWaylandRuntime` and `NucleusThemeAssetIO`; `DequeModule`
attaches only to `NucleusThemeAssetIO`.

Three sites keep a dictionary and a parallel ordering array consistent by hand,
and each repeats the removal logic across every mutating method:

- `SeatSerialLedger` holds `records` and `order`, and repeats
  `order.removeAll { $0 == serial }` in
  `authorizes(serial:kinds:clientKey:surfaceID:consume:)` and in both
  `invalidate` overloads. This is seat-serial provenance, where the two
  structures diverging means a grant is authorized against a stale record.
- `BoundedThemeAssetIO` holds `completed` and `lru`, and runs
  `lru.removeAll { $0 == key }` on every cache hit through `touch(_:)`.
- `XdgActivationManager` holds `grants` and `grantOrder` in the same shape.

Each collapses to one `OrderedDictionary` whose explicit element order is the
eviction order. Key assignment does not make an existing entry most-recently
used, so `BoundedThemeAssetIO.touch(_:)` explicitly moves the existing element
to the end. Key removal remains O(count), so this is not a complexity-class
change; it removes the possibility of keyed state and eviction order
disagreeing.

`BoundedThemeAssetIO` also uses `pending` as an unbounded FIFO with
`pending.removeFirst()` in `resolve(_:)` and `finish(_:value:)`. That becomes a
`Deque`, which is a genuine O(n) to O(1) change on the admission path.

The bounded FIFOs stay `Array`. `IconThemeResolver.themeChain()` caps at sixteen
entries and `PerOutputRenderRects.put(_:_:)` caps at the tracked-output limit;
`Array` is the correct structure at those sizes and neither is converted.

Gate: `collider test compositor` and `collider test core` pass, with
`SeatSerialLedger`, `XdgActivation`, and `BoundedThemeAssetIO` behavior covered
by their existing suites. Cache-hit coverage proves that touching an existing
entry moves it to the eviction tail. `Package.resolved` shows no version change.

## Phase 3: Standard-library synchronization replaces residual manual locks

`swift-atomics` is not adopted, and this phase closes the gap that its evaluation
exposed instead.

The Swift side is already on the standard library: `Synchronization` is imported
across the first-party graph, with `Atomic` and `Mutex` carrying concurrent
state. Every remaining atomic is `std::atomic` in C++ (`Graphite.cpp`,
`DeviceEventEmitter.cpp`, `TextRegistry.cpp`,
`NucleusPlatformTimerRegistry.cpp`) or C in the gfxstream shared ring, where
Swift neither owns nor should own the storage. The one capability
`swift-atomics` has that the standard library lacks — `UnsafeAtomic` constructed
over an existing mmap'd address — is precisely the shared ring, whose guest side
is C in AOSP; moving those atomics into Swift would break the guest.

Ten manual lock declarations remain across seven Nucleus-owned Swift files.
Production owns three: one `NSLock` in `SwiftPackageGraphResolver.swift` and two
in `AppleContainerLifecycle.swift`. Collider test support owns six `NSLock`
declarations across `CommandConsoleTests.swift`, `RunProgressReporterTests.swift`,
`RepositoryCacheTests.swift`, and `RunTerminalSummaryTests.swift`.
`VulkanLaneTestSupport.swift` owns one `pthread_mutex_t`. Each moves to `Mutex`
over the state it actually guards, and each now-unnecessary
`@unchecked Sendable` annotation is removed.

Gate: `collider test all` passes. No Nucleus-owned Swift source outside vendored
third-party and `swift-sdk/source` trees declares `NSLock`, `pthread_mutex_t`, or
`os_unfair_lock`.

## Phase 4: One terminating sequence replaces the Collider progress side task

`swift-async-algorithms` becomes a declared dependency of `collider`, and the
`AsyncAlgorithms` product attaches to `ColliderCLI`.

`consumeRunObservations(_:console:registry:run:)` currently combines a repaint
ticker with the run-observation stream by spawning a side `Task` that sleeps in
a loop, then tears it down through `defer { ticker.cancel() }`. The ticker and
the observation loop call `RunProgressReporter` from separate tasks, leaving
cross-source arrival ordering to actor scheduling.

A shared event enum carries `.observation`, `.pulse`, and `.finished`.
`chain(observations.map(Event.observation), [Event.finished].async)` appends one
terminal event to the finite observation branch. That branch is merged with an
`AsyncTimerSequence` mapped to `.pulse`, and one serial `for await` handles every
event. The loop breaks on `.finished`, which retires the merged iterator and
cancels the infinite timer branch before calling `RunProgressReporter.finish()`.
The design guarantees one consumer and explicit termination; it preserves the
merged sequence's arrival order and claims no deterministic ordering for events
that become ready simultaneously.

`RunProgressReporter` keeps its hand-written throttle. `minimumAppendInterval`
and `lastEmissionDate` in `canEmit(at:)` express what `_throttle` expresses, but
that operator is still underscored in 1.1.5 and is not adopted.

`ProcessRunner.run` is not converted. Its `withThrowingTaskGroup` races a command,
a body, and a cancellation signal to a single winner; that is a task race, not a
stream combination, and `TaskGroup` is already the right structure.

Gate: `collider test collider` passes. `ColliderCLITests` prove observation
delivery, repaint cadence, one final render, natural observation-stream
completion, caller cancellation, and the absence of pulses after `.finished`.
A build with progress reporting active preserves the current repaint cadence.

## Rejected surfaces

`swift-atomics` is rejected for the reasons in Phase 3. The standard library
covers first-party Swift, and the remaining atomics belong to C and C++ at
boundaries Swift does not own.

`swift-algorithms` is rejected. The candidate sites are a handful of
`var seen = Set<...>` accumulation loops in `RenderCoreOutputs`,
`GraphicsContract`, and the Vulkan generator that `uniqued()` would shorten, and
one `stride(from:to:by:)` batch loop in `CoreColliderRecipe` that
`chunks(ofCount:)` would express. These are cosmetic and do not justify a
declared dependency.
